# ADR 0018 — Pull request previews behind the gateway

- **Date:** 2026-08-10
- **Status:** Accepted

## Context

R12 asks that each pull request publish a rendered preview to an isolated URL, that the link be
visible on the CMS workflow card and as a pull request comment, and that the artifacts be deleted
on merge or close. It is a P1 requirement and the second half of Phase 3, the pilot — an author who
cannot see their page rendered before it merges cannot complete a documentation task unaided, which
is the phase's exit condition.

The conventional shape for this is a bucket behind a CDN: build the site per pull request, sync it
to `s3://previews/pr-42/`, and hand out a CloudFront URL. Every hosted platform works that way and
it is cheap to describe.

It is also, here, a way of putting unreviewed drafts of the handbook on the public internet. The
corpus holds people-operations and finance content — that is the premise of open question Q11 and
of [ADR 0016](0016-recording-documentation-gaps.md). The published site is served from an
application load balancer that a real deployment sets to `internal`. A CloudFront distribution in
front of a preview bucket has no such setting: it is public unless signed URLs, a WAF or Lambda@Edge
are added, each of which is a second authentication story to build, test and keep working.

There is a related trap in the storage. Putting previews under a prefix in the corpus bucket looks
tidy and costs nothing, but R21 says preview builds are never ingested — and the corpus bucket _is_
the knowledge base's data source. That constraint would then rest on a prefix filter in the data
source configuration, one edit away from indexing a hundred unmerged drafts.

## Decision

**The gateway serves previews, from a private bucket of its own.**

1. **A second bucket, never the corpus bucket.** `PreviewSite` creates
   `<stack>-previews`: private, encrypted, unversioned and `forceDestroy: true`. Bedrock has never
   been pointed at it, so R21 holds by construction rather than by configuration. It is
   unversioned and disposable because a preview is regenerated by pushing again — the corpus is
   versioned so that a retraction is reversible, and a preview has no such claim on us.
2. **The gateway serves `/previews/pr-<n>/`,** reading from that bucket, mounted before the site
   catch-all and after the API routes. A preview is therefore reachable by exactly the people who
   can already reach the documentation site, with no second access-control mechanism to get wrong.
3. **No CloudFront, and no public URL.** The base URL handed to authors is the load balancer's.
4. **The workflow publishes and deletes.** `.github/workflows/preview.yml` builds with
   `DOCUSAURUS_BASE_URL=/previews/pr-<n>/`, syncs with `--delete`, comments the link, and on
   `closed` — merge or close, both — removes the prefix and rewrites the comment. A 30-day
   lifecycle rule is the backstop for the run that never happens, not the mechanism.
5. **The CMS card asks the gateway.** Decap's `getDeployPreview` is answered from the entry's
   newest submission: an open pull request yields `pr-<number>/`, anything else yields `null`.
   Nothing has to tell the CMS what the workflow did.
6. **Both halves or neither.** `PREVIEW_BUCKET` is a master switch and `PREVIEW_BASE_URL` becomes
   required with it, following [ADR 0009](0009-fail-closed-configuration.md). A deployment that
   configures a bucket and no URL fails at start-up rather than offering authors a broken link.

## Consequences

**Preview traffic goes through ECS.** Every asset of every preview is a `GetObject` served by a
task that also answers reader questions. This is the real cost of the decision. It is accepted
because the audience is a pilot's worth of authors and reviewers rather than the readership, and
because the alternative buys throughput with a public URL. If preview traffic ever becomes a
noticeable share of the service's load, the fix is a CDN _inside_ the boundary, not a public one.

**Pull requests from forks get no preview.** A fork's `pull_request` token carries the fork's OIDC
subject and cannot assume the preview role. The workflow detects this and skips with a notice
rather than failing. For an internal handbook whose pull requests are opened by the CMS on
`cms/*` branches in this repository, that is the normal case rather than a limitation.

**A preview is only as isolated as its key prefix.** The role can write under `pr-*` and the task
can read under `pr-*`; `resolvePreviewRequest` refuses anything that would resolve outside the
requested pull request's prefix, before any S3 call. That function is pure and its whole refusal
table is a unit test, for the same reason `kb/key-policy.ts` is.

**This is unexercised against real AWS.** The component and the workflow ship reviewed but not
deployed — this repository's stack has never been applied. The same honesty
[ADR 0013](0013-two-authentication-modes.md) applies to ALB auth mode applies here.

## Alternatives considered

**S3 and CloudFront.** Rejected above: a public URL in front of unmerged internal content, or a
second authentication mechanism to build.

**GitHub Pages.** Free and simple, and public — the same objection, with less control.

**A workflow artifact.** A downloadable zip is not a rendered preview at a URL. It fails R12's
first criterion and gives the CMS card nothing to link to.
